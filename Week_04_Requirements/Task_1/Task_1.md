# Task 1 Assignment

Your task is to design and implement an agentic network for software requirements refinement. The agentic network should be capable to accept a corpus of various texts describing software and its features, and provide a structured document of requirements on the output. You only need to debug it on the provided example; however, the network should be prepared to work with similar examples (e.g. do not hard-code input file paths, only provide path to input directory). You are not just allowed, but also required to use your coding agent to help you create the network.

Your nodes in the network should use OpenAI API, with the key you received in email.
You have access to these models (use any you like):
- gpt-6-luna
- gpt-5.6-luna
- gpt-5.4-nano
- gpt-5-nano
- gpt-5-mini
- gpt-4.1-nano
- gpt-4o-mini

## SPECS OF THE AGENTIC NETWORK:
- ANS1. At least 3 agentic (LLM-invoking) nodes 
- ANS2. At least 1 deterministic (non-AI) node
- ANS3. At least 1 feedback loop (i.e. 1 node checks output of other node, possibly looping)
- ANS4. At least 3 different LLM models (for our labs it is okay if they are from the same vendor).
- ANS5. Implemented in Python's LangGraph framework

## SPECS OF THE AGENTIC NETWORK'S OUTPUT:
- OS1. Single structured document
- OS2. Unique identification of each requirement
- OS3. No (semantically) duplicate requirements
- OS4. Tracing - for each requirement, from which input documents was it derived?
- OS5. Each requirement should have a short descriptive name and a paragraph-long explanation
- OS6. Each requirement should have assigned its priority; priority scale should be explained in the document
- OS7. Consistency across requirements - consistent language and vocabulary, no semantically contradictive/conflicting requirements
- OS8. Completeness - Make sure not to ignore requirements from the input documents
- OS9. Blacklist - if an identified requirement is discarded because it is confliting, or nonsensical, it should also be recorded in separate section with explanation why it was discarded
- The output of your agentic network does not have to meet the output specs (OS#) perfectly (e.g. if your underlying model is weak), but each spec should be addressed by some element in your agentic network (specialized agent, a sentence in prompt prompt, ...).

## POINTS AWARDED FOR SUCCESSFUL COMPLETION: 5b

## OUTPUT:
- A Python script (or a set Python scripts) that implement the agentic network
- A report with your agentic network design choices explained
- A structured document of requirements corresponding to the input corpus of documents, generated by your agentic network


Elicitation:

Tabuľka v súbore inputSources.txt reprezentuje prvú časť sekcie Elicitation -> Identification of stakeholders and other sources of requirements. Identifikuje s akými súbormi v tejto úlohe budem pracovať, ich typy, obsah a cestu k ním. Tabuľka mapuje zdroje požiadaviek, ktoré sieť má preskúmať (nie finálny zoznam požiadaviek).

Gathering of raw requirements: Ďalšia tabuľka opisujúca jednotlivé potreby zo zdrojov v súbore elicitation_candidates.json. Vytvorí ju samotná sieť po tom ako agent prečíta dokumenty. Pri každej požiadavke agent zaznamená zdroj a textový dôkaz. Finálny dokument požiadaviek bude vytvorený z medzivýsledkov zoznamov.

Plán implementácie:

1. Načítanie súborov zo vstupného adresára -> Načítanie textu zo vstupného adresáru a priradenie ID zdroja. Input : PATH adresáru, Output : Zoznam dokumentov zo zdrojmi

2. Výber kandidátov -> Výber požiadavok z dokumentov a ich zdroje a úryvky. Input : (gpt-6-luna) LLM agent dostane jednotlivé dokumenty, Output : Kandidátne požiadavky

3. Zjednotenie -> Zoskupovanie kandidátov a ich zjednotenie. (jednotný jazyk) Input : (gpt-5.6-luna) Druhý LLM agent dostane kandidátne požiadavky, Output : Zjednotené požiadavky + zoznam missing candidates po zjednotení

4. Overenie -> Identifikácia nejasností, chýbajúcich požiadaviek. Input : (gpt-5.4-nano) Tretí LLM agent dostane pôvodných kandidátov a aktuálne zjednotené požiadavky, Output : list problémov a návrhov na opravu

5. Oprava (LangGraph - feedback loop) (gpt-5.6-luna) -> Ak existuje problém, vráti nový výsledok na zjednotenie a overenie. Input : Výsledok overenia, Output : Opravený návrh

6. Kontrola a vytvorenie finálneho dokumentu (gpt-5.6-luna) -> Vytvorí finálny dokument ak nechýbajú povinné časti. Input : schválené požiadavky, Output : dokument

Implementácia:

load.py -> načítanie a overenie dokumentov, prvý deterministický krok. Pripravuje dokumenty ako vstupy pre ďalšie kroky siete. Funkcia find_files vráti zoradený zoznam ciest k nájdeným súborom so suffixom .txt alebo .eml
Funkcia load_file vracia slovník pre každý dokument. Zoznam obsahuje tieto hodnoty: ID, path, f_type a text
Funkcia compare_with_inputSources_table(documents, t_path) porovná cesty načítaných dokumentov s cestami dokumentov v ručne vytvorenej tabuľke inputSources.txt.

candidates.py -> kandidátne požiadavky a uloženie kandidátnych pož. do JSON súboru. Je to prvý LLM krok siete. Model vyberá kandidátne požiadavky, otázky a návrhy. Používa funkcie z load.py na načítanie dokumentov. Funkcia choose_cand má na vstupe OpenAI klienta a jeden dokument. Pomocou špecifického promptu model vytvorí (vyberie) z dokumentu tvrdenia vzťahujúce sa na softvérové požiadavky. Každý kandidát uchováva o sebe tieto informácie : candidate_text, evidence(citácie), kind(typ), uncertainties(nejasnosti). Každý kandidát potom dostane svoje unikátne ID a taktiež aj cestu ku zdrojovému dokumentu. Výsledných kandidátov zapíše do JSON súboru elicitation_candidates.json . Predstavuje medzivýsledok časti elicitation.

zjednot.py -> Zjednotenie kandidátskych požiadaviek, druhý LLM krok siete. Zo súboru elicitation_candidates.json načíta a zoskupí kandidátov s rovnakými potrebami. Pôvodný kandidáti sú bez zmeny a nový zjednotení sú v novom súbore zjednotene_requirements.json . Funkcia zjednot_davku_kandidatov(candidates, a) spracuje jednu dávku 20tich kandidátov. Vytvára vstup obsahujúci : ID povodnych kand., candidate_text, kind. Tento zoznam vytvára ešte pred odoslaním modelu. Funkcia zjednot_kandidatov(candidates, a) vytvára mapu pôvodných kandidátov podľa id, rozdeluje kandidátov do dávok veľkosti 20 a každá dávka putuje do funkcie zjednot_davku_kandidatov(candidates, a). Výsledky dávok znova prechádzame aby sme mohli zjednotiť aj kandidátov, ktorý vznikli v iných dávkach. Po normalizácií im priradíme normalized_id. Dôkazy a zdrojové cesty nových kandidátov dohľadávame podľa candidate_ids. Kandidáti, ktorých model nezahrnul, vloží do samostatného zoznamu missing_candidates.

over.py -> Overenie zjednotených kandidátov, tretí LLM krok siete. Funkcia review(candidates, zjednoteny_candidates, a) vkladá do promptu skupinu pôvodných a zjednotených kandidátov. V prompte od modelu žiadam aby: identifikoval problémy na základe údajov, hľadal nejasnosti, hľadal nesprávne zlúčených kandidátov, hľadal stratené detaily a nevykonáva žiadne opravy.
Vytvorený JSON súbor obsahuje issues - teda aký je problém, ktorých ID sa problém týka a návrh ako problém riešiť.
Kandidátov a zjednotené požiadavky spracováva v batchoch o veľkosti 10. Následne všetky nálezy spojí.

oprav.py -> LangGraph workflow, načíta pôvodných kandidátov, zjednotených a nálezy z report.json . Funkcia missing nájde kandidátov, ktorý boli vynechaný po zjednotení. Funkcia back_missing ich obnoví aj jednotlivé položky. Funkcia prep_batches priradí nálezy ku konkrétnym zjednoteným položkám a rozdelí ich do dávok. Funkcia repair_batch požiada model o návrhy úprav textu. Uzol rep - obnova, opravy. Uzol rew volá funkciu review z over.py a vypočíta chýbajúce ID. Pomocou LangGraph-u buď pokým neexistujú nálezy chýbajúcich kandidátov alebo do posledného kola = 2, vykonávame feedback slučku medzi týmito uzlami. Funkcia final zapisuje výsledky do requirements_after_step5.json . (po obnove mám 0 vynechaný kandidátov)

final.py -> Finálny dokument požiadaviek. Načíta opravené položky z výsledku oprav.py a nevyriešené nálezy oprava_report.json . Model spracúvava položky po batch = 10 a pre každú navrhne krátky názov, vysvetlenie v odseku a prioritu. K vygenerovaným údajom potom doplníme pôvodné ID kandidátov, zdrojové dokumenty a dôkazy. Výsledok je rozdelený na požiadavky, návrhy, otvorené otázky a ostatné položky. (final_requirements.json)
